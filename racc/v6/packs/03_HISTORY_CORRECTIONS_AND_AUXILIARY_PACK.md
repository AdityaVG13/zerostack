                                                     Abstract

         Tool-output compaction can reduce the nominal length of an agent transcript while simultaneously
     destroying the exact prefix on which provider prompt caching depends. This creates a cache-compaction
     paradox: a shorter prompt can be more expensive than a longer cached prompt, particularly when the
     edited tool block is followed by a long already-cached suffix. ZeroStack resolves the paradox by moving
     compression earlier and state outward. Large tool results are captured before first model exposure,
     stored as immutable content-addressed objects, and represented in model-visible history by stable
     decision capsules and exact expansion handles. The visible history is append-only; expansion appends
     evidence rather than rewriting the past. Beneath that history, ZeroStack maintains a persistent causal
     cache whose objects are keyed by constructor identity, dependency roots, and execution contracts.
     Project changes invalidate only the dependency-complete descendant cone, while unchanged objects
     remain reusable across turns, sessions, branches, harnesses, and provider-cache eviction. We formalize
     this architecture as the Causal Cache Normal Form, prove a Retrospective Rewrite Theorem, a
     Cache-Compaction Break-Even Theorem, a First-Emission Prefix Preservation Theorem, Causal

     Transposition result, and two-tier Q99 laws. The resulting moat is precise: ZeroStack cannot prevent
     a provider from evicting its own cache, but it can prevent its own compaction from breaking exact
     prefixes, prevent provider eviction from causing project amnesia, and prevent unrelated project changes
     from triggering global rediscovery. Q99 is then a measured property of retained causally valid project
     mass, not a slogan attached to a provider TTL.

1      The cache-compaction paradox

Coding-agent harnesses repeatedly resend a growing model-visible history containing instructions, prior
reasoning, tool calls, file contents, command outputs, diagnostics, and edit results. Contemporary
systems attack this growth in several ways: output truncation, log filtering, summaries, retrieval-backed
compaction, tool-schema compression, or code-mode composition. These methods solve real problems.
They do not, however, optimize the same cache object.
Provider prompt caching generally reuses computation only when an eligible prompt prefix matches
exactly. OpenAI documents exact matching at cache breakpoints and warns that changing tool history,
tool definitions, ordering, schemas, or earlier prompt content can prevent a cache hit; OpenAI’s Codex
engineering discussion similarly emphasizes append-only history and deterministic tool ordering as cache-
preserving design choices [14, 15, 13]. Anthropic exposes automatic or explicit prefix breakpoints with
finite cache lifetimes, and xAI likewise documents exact starting-message reuse and cache misses after
earlier-message modification or reordering [4, 18, 19].
A router that first inserts a large tool result into history and later replaces it with a short note may
therefore reduce future prompt length but destroy the exact downstream prefix. Whether that trade is
favorable depends on the removed block, the already-cached suffix after it, provider read and write prices,
cache residency, and the number of future turns. The correct response is not to reject compaction. It is
to change when and where it occurs.


    Draft 4 cache thesis
    Do not place a large object into model-visible history and then mutate the past to remove it. Capture
    the object before first exposure, preserve it exactly in a durable causal store, expose a stable decision
    capsule from the beginning, and append exact expansion evidence only when the model requests it.


This paper calls that architecture reference-first causal caching. It combines two distinct protections:

1. prefix stability: model-visible history does not retroactively change;
2. project-state durability: exact project objects survive provider-cache eviction and are invalidated
   by causal change rather than idle time.

Neither alone is sufficient. A stable prompt can still be enormous. A durable project index can still flood
the model with raw intermediate results. Their combination is the Q99 moat.

2     Three cache objects, not one

The word “cache” hides three different objects.


2.1   Provider prefix cache

A provider prefix cache stores model-side computation associated with a rendered prompt prefix. Its hit
event depends on exact prefix identity, model and request compatibility, routing, an eligible breakpoint,
and provider-controlled residency. It can reduce price and latency but is not durable project memory.


2.2   Harness transcript cache

A harness transcript records what has been shown to the model. Its design controls whether prior
messages remain stable, whether large outputs are inserted verbatim, and whether later compaction
rewrites earlier content. This layer determines the shape presented to provider caching.


2.3   ZeroStack causal project cache

A ZeroStack causal cache stores exact project objects, indexes, derived facts, task lenses, tool outputs,
verification results, and continuation state. Its semantic validity is determined by dependency roots and
contracts. The same object can remain reusable after a provider cache expires, after a conversation closes,
or on a different branch whose relevant dependency roots are unchanged.

Definition 2.1 (Cache-layer coordinates). For an invocation, define:

                            HP := provider prefix-cache hit event,
                            HT := stable harness-history identity event,
                            HZ := causally valid ZeroStack object-hit event.

These are separate events. A provider miss does not imply a ZeroStack miss, and a ZeroStack hit does
not imply that the provider retained model-side computation.

The distinction is essential for measurement. “Ninety-nine percent caching” must name the coordinate:
cached provider tokens, exact indexed object mass, avoided model-visible project tokens, avoided primitive
tool calls, or complete work.

4    The Causal Cache Normal Form

The cache-compaction paradox disappears when the harness never needs to rewrite old model-visible
output. Draft 4 defines a canonical form.

all of the following.

1. Reference-first capture. A large tool result O is captured by ZeroStack before first model exposure.
2. Immutable object storage. The exact result is stored under a content root r = H(O) together with
   its formation and dependency receipts.
3. Stable first emission. The first model-visible representation is a canonical capsule

                                             c = Capsule(r, η, e),

4. Append-only visible history. Past model-visible bytes are never changed. New decisions, expansions,

5. Causal rather than temporal validity. Project objects are reusable while their complete dependency
   and contract roots remain valid.
6. Versioned mutation. Project changes create new roots; they do not rewrite the identity of old

7. Scoped authority. A capsule does not authorize an edit or factual claim beyond the evidence and
   verifier scope bound into its receipt.

16    Why causal caching is a moat rather than another compactor

Existing systems attack important portions of context cost. Context Mode intercepts and indexes large
outputs, RTK compacts command output, and Headroom compresses tool results and supports retrieval
of originals [6, 16, 9]. Code Mode reduces tool-schema and orchestration exposure by allowing an agent
to write a program that privately calls APIs; Cloudflare reports a fixed two-tool surface of about one
thousand tokens for an API that would otherwise expose roughly 1.17 million schema tokens [5].
ZeroStack’s intended moat is the conjunction of five properties:

1. reference-first rather than retrospective: large outputs never need to be rewritten out of the
   transcript;
2. exact durable objects: full originals, derivations, and receipts persist outside provider TTLs;
3. causal invalidation: project changes update only the dependency-complete affected region;
4. private multi-tool composition: the backend performs mechanical discovery and execution without
   exposing every intermediate result;
5. decision-boundary sufficiency: the model receives enough exact evidence to preserve reasoning
   and native-tool strategies, with expansion and fallback available.

A compactor can save transcript tokens. A provider cache can discount stable prefixes. A code-mode
layer can reduce tool schemas and calls. A repository index can retrieve files. The Pareto opportunity
arises from composing them under one exact recovery and accounting contract.


17    Relationship to incremental computation and build systems

Causal caching is not invented from nothing. Build systems use persistent metadata, hashes, dependency
tracking, and early cutoff to avoid repeated work; Build Systems à la Carte formalizes schedulers,
rebuilders, and persistent stores across systems such as Make, Shake, Bazel, and Excel [12]. Shake
emphasizes dynamic dependency discovery and dependency checking [11]. Self-adjusting computation
records dynamic dependence graphs and propagates input changes through affected computation [1, 3].
Leases formalize time-based distributed-cache consistency, highlighting the distinction between correctness
and residency/performance [8].
RACC-Q99’s candidate contribution is to transpose these ideas to a model-visible harness boundary with:

• exact provider-prefix constraints;
• reference-first tool-result capsules;
• protected decision sufficiency;
• task-relative project lenses;
• model/harness rendering layers;
• one-/two-call private tool composition;
• no-degradation fallback and authority;
• a unified token, byte, work, and quality ledger.

18     Limits and falsifiers

18.1    Index incompleteness

If ZeroStack omits a dependency that can change a cached object, theorems 7.1 and 8.1 do not apply.
A runtime observation of an undeclared file, environment variable, process result, tool version, network
response, or configuration input is a direct falsifier of the current causal certificate.


18.2    Nondeterminism

A constructor whose output depends on unbound randomness, time, concurrency, network state, or
hardware behavior cannot be treated as deterministic. Such factors must be bound as dependencies,
represented distributionally, verified after execution, or marked Unknown.


18.3    Decision-view insufficiency

A capsule can be stable yet insufficient. If the model’s protected decision changes when hidden evidence
is revealed, the current capsule is not a valid decision view for that scope. The system must expand
evidence and record the counterexample.


18.4    Physical storage and maintenance

Durable logical reuse can impose storage, indexing, verification, and invalidation costs. Q99 indexed
reuse is not Q99 complete work. The Pareto paper measures the complete resource vector.


18.5    Provider behavior

Theorems about exact identity do not guarantee provider residency, pricing, routing, or future pol-
icy. Provider documentation must be treated as time-indexed operational context, not a permanent
mathematical premise.

  Novelty and epistemic status.
  The Retrospective Rewrite Theorem is a direct consequence of exact-prefix matching; content-

  priority for that complete composition. Independent literature review and peer assessment remain

19    Conclusion

The cache frontier is not won by deleting more old text after it has already entered the conversation.
That maneuver can reduce prompt length while invalidating the provider prefix that made the longer
prompt inexpensive. The stronger architecture changes the lifecycle of information.
ZeroStack captures large tool outputs before first model exposure, preserves the exact object under a
durable causal root, emits a stable decision capsule, appends expansions rather than rewriting history, and
reuses project state according to dependency validity rather than provider TTL. Provider prompt caching
remains valuable: it becomes an L1 accelerator for a compact, append-only control history. ZeroStack is
the L2 authority that keeps the project known.
The defensible “never break the cache” result is therefore threefold:

1. ZeroStack does not break exact prefixes through its own retrospective compaction;
2. provider eviction does not cause full project rediscovery while the causal closure remains retained and
   valid;
3. project changes invalidate only the dependency-complete affected region rather than the entire session
   or repository.

Q99 is achieved when the invalidated task-relevant causal mass stays below one percent and the complete
maintenance cost remains beneath the declared Pareto threshold. It is not guaranteed by a label. It is a
measurable consequence of prefix-stable history, durable exact objects, fine-grained dependencies, and a
workload whose novelty is sparse enough to reuse what has already been learned.

Provider caches are L1 accelerators. ZeroStack L2 logical causal validity must not depend on provider residency. A provider miss may reprocess a compact decision view, but should not cause unchanged repository discovery while valid L2 state remains retained.
