# Benchmark integrity policy

Binding policy for every performance or quality number published from this
repo: README, docs, demo artifacts, competitor bake-offs, and northstar bead
claims. Tracked as bead `fszero-ltr`; a benchmark bead closed without meeting
this policy gets reopened.

Project-level numeric budgets (aspirational vs gated) live in
[`BUDGETS.md`](BUDGETS.md). This file owns measurement honesty; BUDGETS owns
the northstar contract values.

## Rules

1. **Real numbers only.** Every reported number is honestly measured and
   reproducible. No cherry-picked corpora, no dropped losing cases, no
   benchmark-specific special-casing in product code, no tuning on the eval
   set and then reporting it as held-out, no self-graded success without a
   committed methodology.
2. **Committed runner.** Every benchmark ships a committed runner script so
   anyone can regenerate the number from a clean checkout
   (`./scripts/benchmark.sh` for the README table).
3. **Committed corpora and gold sets.** Corpora and gold sets are committed
   or generated by committed scripts -- never hand-curated after seeing
   results.
4. **Fair baselines.** Baselines and competitors run under identical
   conditions as the candidate, at their best documented configuration, not
   strawman defaults. RAG baselines include their index/embedding build cost.
5. **Losses get published.** Any regression or loss discovered is filed as a
   bead and published alongside wins -- never silently removed from a corpus
   or report.
6. **Cited provenance.** Headline numbers cite the exact benchmark commit
   that produced them. Artifacts keep `git_commit`, `git_dirty`, `hardware`,
   and `date`, and embed `scenario_fingerprint` from
   `scripts/env_fingerprint.py`. The fingerprint requires CPU/cores,
   power/governor status, kernel, rustc and Cargo profile, filesystem/mount,
   isolation, `cache_state` (`cold`, `warm`, `mixed`, or `varies`), `run_id`,
   and `captured_at_utc`; unavailable probes stay explicit. Committed artifacts
   must have `git_dirty: false` (tracked files match the cited commit; corpus
   stats describe whatever was on disk at measurement time, including
   untracked files). The artifact file itself is excluded from the dirty check
   -- it is the run's own output.

## Honest-gate for comparative publish

Comparative / competitor tables (bake-offs, head-to-head README rows, peer
suites) require a co-located **honest-gate attestation** before numbers leave
the host as published claims. Schema: `fszero.honest_gate` JSON with exactly
**14 questions**, each status one of:

| Status | Meaning |
| :-- | :-- |
| `pass` | Affirmed with evidence string |
| `fail` | Hard no -- do not publish until fixed |
| `waive:<reason>` | Intentional exception; reason is load-bearing |

Questions (ids stable):

1. `Q01_same_build_profile` -- declared build profiles (release-perf for FSZero stack claims)
2. `Q02_api_workload_match` -- same corpus and success predicate (or STATE-labeled)
3. `Q03_warmup_symmetry` -- warmup symmetry or process-model STATE labels
4. `Q04_sample_count_n` -- n>=20 or explicit conservative-tail exception
5. `Q05_host_quiet` -- isolation / quiet host note
6. `Q06_variance_envelope` -- ordered trial vector or envelope
7. `Q07_three_tier` -- p50/p95/p99 or documented median-only reason
8. `Q08_losses_published` -- losses and exclusions published
9. `Q09_apples_flags` -- best documented competitor config
10. `Q10_reproducible_runner` -- committed runner
11. `Q11_git_dirty_false` -- committed artifact `git_dirty: false`
12. `Q12_process_model_labels` -- long-lived MCP vs spawn vs in-process
13. `Q13_tool_order_cache` -- tool-order / page-cache fairness
14. `Q14_claims_audit` -- inventory / claims_audit / provenance complete

**Tooling:** `./scripts/honest_gate.sh --out PATH --artifact PATH --label NAME`
writes a template; edit statuses; `./scripts/honest_gate.sh --check PATH`
rejects any hard `fail`.

**Waivers for intentional STATE axes:** fff in-process vs CLI-less design,
`fszero-server` vs `fszero-spawn`, watchman daemon settled vs fszero one-shot
index update -- these are **STATE** comparisons, not MATCH peer ranks. Record
them as `waive:…` on Q02/Q03/Q12 rather than claiming identical work.

**Co-location:** next to the competitive artifact, e.g.
`benchmarks/honest_gate_bakeoff.json` beside `benchmarks/bakeoff.json`, and
`benchmarks/honest_gate_watch_bakeoff.json` beside `benchmarks/watch-bakeoff.json`.
Regenerate attestations when regenerating numbers.

## Process-model axis for peer tables

Published comparison tables (README, bake-offs, competitor suites) must state
each row's **process model** so readers do not treat spawn-inclusive walls as
steady-state op latency:

| Label | Meaning |
| :-- | :-- |
| `long-lived MCP` | Persistent `--mode=mcp` (or equivalent) session; index may be pre-warmed. |
| `process-spawn` | Fresh process per timed trial (startup inside the timer). |
| `scratch-repo spawn` | Spawned process over an ephemeral/scratch repository. |
| `n/a` | Non-latency row (corpus size, counts). |

**Peer rule:** absolute ms rows may be compared only when process model **MATCH**es,
or the comparison is explicitly labeled **STATE** (different models, narrative only).
A CodeMode plan measured as process-spawn must not be peer-ranked against warm MCP
p50 without that STATE label (see closed bead `fszero-heem`). Bakeoff dual-mode
(`fszero-server` / `fszero-spawn`) already separates these axes.

## Environment fingerprint

Capture the environment before every published performance run. Give the run
an explicit ID and describe isolation, power, cache, and competing-load state:

```bash
mkdir -p /tmp/fszero-perf-example
FSZERO_PERF_RUN_ID=example \
FSZERO_PERF_CACHE_STATE=mixed \
FSZERO_PERF_CARGO_PROFILE=release-perf \
FSZERO_PERF_ISOLATION_NOTE="idle host; AC power; no competing load" \
  uv run python scripts/env_fingerprint.py \
  > /tmp/fszero-perf-example/fingerprint.json
uv run python -m json.tool /tmp/fszero-perf-example/fingerprint.json >/dev/null
```

The JSON records CPU, power/governor availability, kernel, Rust toolchain and
Cargo profile, filesystem/mount, tracked git state, structured cache state,
run ID, UTC capture time, and the isolation note. An unavailable host probe
stays explicit; it never becomes an inferred value. Keep the fingerprint
beside the raw trial vector.

Absolute latency gates and comparisons require the same declared host class:
CPU model and core count, operating-system family and machine architecture,
filesystem type, power/governor state, rustc identity, and Cargo profile. A
mismatch needs a separately calibrated threshold and must not be described as
a same-host comparison. Undeclared cache state, missing isolation notes,
thermal throttling, or competing heavy load invalidates an absolute-latency
run; rerun it instead of explaining away the result.

## Host class identity (CI vs published local)

Absolute latency numbers are host-class-bound. A number measured on one class
must not gate or peer-rank another class without an explicit recalibration.

### Declared classes

| `host_class` label | Where | Role |
| :-- | :-- | :-- |
| `local-m5-max` | Developer Mac with Apple M5 Max (primary published host) | Absolute baselines in README, `benchmarks/demo-bench_results.json`, scaling suites, and northstar artifacts. |
| `local-apple-*` / `local-darwin-*` / `local-linux-*` | Other local machines (auto-derived from CPU/OS) | Local exploration only; never overwrite `local-m5-max` published baselines without a re-baseline bead. |
| `gha-ubuntu-latest` | GitHub Actions `runs-on: ubuntu-latest` | Ephemeral Linux runners. **Relative** ratchets and tracked-fail history only -- not absolute µs peers of M5 Max. |
| `gha-macos-latest` / `gha-<ImageOS>-<arch>` | Other GHA images | Same rule: CI class is not `local-m5-max`. |
| Override via `FSZERO_PERF_HOST_CLASS` | Any | When auto-derivation is wrong; record why in the isolation note. |

`scripts/env_fingerprint.py` stamps `host.host_class` (and
`host.runner_image` on CI) into every fingerprint. On GitHub Actions it reads
`GITHUB_ACTIONS`, `ImageOS`, `ImageVersion`, and optional
`FSZERO_PERF_RUNS_ON` (set this to the workflow `runs-on` label so artifacts
say `gha-ubuntu-latest` rather than a raw image codename).

### Comparison policy

1. **Absolute latency gates** (hard µs/ms ceilings from committed artifacts)
   may fire only when the run's `host.host_class` **equals** the baseline
   artifact's `host.host_class` (or the baseline's documented class when the
   older artifact lacks the field -- treat missing as `local-m5-max` only for
   historically labeled M5 Max demo artifacts, otherwise reject).
2. **CI (GHA) default:** use **relative** ratchets (percent drift vs the last
   accepted same-class CI baseline) or tracked-fail history. Do **not** compare
   GHA walls to `local-m5-max` absolute numbers and call it a gate.
3. A host-class mismatch needs a separately calibrated threshold and must be
   labeled **STATE** (different class), never a same-host pass/fail.
4. When CI emits bench/perf artifacts, provenance **must** include:
   - `host.host_class` (e.g. `gha-ubuntu-latest`)
   - `host.runner_image.image_os` + `image_version` (GHA `ImageOS` /
     `ImageVersion`) when available
   - `FSZERO_PERF_RUNS_ON` mirrored into `host.runner_image.runs_on`

Example CI stamp:

```bash
export GITHUB_ACTIONS=true   # set by the runner
export FSZERO_PERF_RUNS_ON=ubuntu-latest
export FSZERO_PERF_HOST_CLASS=gha-ubuntu-latest   # optional explicit pin
export FSZERO_PERF_RUN_ID="gha-${GITHUB_RUN_ID}-${GITHUB_RUN_ATTEMPT}"
export FSZERO_PERF_CACHE_STATE=cold
export FSZERO_PERF_CARGO_PROFILE=release-perf
export FSZERO_PERF_ISOLATION_NOTE="GHA ubuntu-latest; shared runner; relative ratchet only"
uv run python scripts/env_fingerprint.py > "$ARTIFACT_DIR/fingerprint.json"
```

## Statistical hygiene

Published latency evidence uses at least 20 measured samples after warmup and
reports p50, p95, and p99 in one unit. An expensive scenario may use fewer
samples only with a written `sample_size_exception`, the exact sample count,
and `conservative_tail: true`; it must report the observed maximum and label
the tail unresolved rather than infer an unsupported percentile.

### Registered sample-size exceptions

These exceptions apply only to the named fields. Every emitted artifact must
repeat the reason, sample count, and `conservative_tail: true` marker.

| runner / phase | n | why repeated raw trials are unavailable | conservative-tail rule | removal condition |
| :-- | --: | :-- | :-- | :-- |
| `search_prefilter_spike`: `queries[].bigram_cold_fill_ms` | 1 | The phase materializes one cold index before the warm vector; an immediate repeat is warm and is not the same workload. | Publish the observed value as the maximum, mark the tail unresolved, and make no p95/p99 or gate claim. | Create at least 20 independent cold indexes and retain their ordered vector. |
| `search_prefilter_spike`: paired cold-ingest wall fields | 1 pair | The frozen decision contract runs one corpus-wide baseline arm and one corpus-wide bigram arm after the same page-cache prime. | Mark the pair conservative, retain both values, and do not use them for a tail claim. | Run at least 20 independent paired rounds without changing the decision workload and retain both ordered vectors. |
| `search_prefilter_spike`: `amortization_bulk_proxy` | 1 pair | This is a historical rejected proxy, not the live decision gate; the runner preserves its original one-pair shape for comparison. | Keep it comparison-only, mark it conservative, and do not infer a percentile. | Regenerate at least 20 independent pairs before making any new claim from the proxy. |
| `watch_bakeoff`: `sizes[].setup` cold-index timings | 1 | Each corpus has one required setup build before the measured change and watch trials; repeating it would be a separate setup corpus. | Report it as conservative setup context only, with no comparison or gate claim. | Use at least 20 isolated setup corpora with an ordered raw vector, or stop publishing setup latency. |

Artifacts retain the ordered raw trial vector, including failed trials with
their status. A runner declares its warmup count, whether warmups enter the
sample, and its outlier rule before measurement. Never drop an outlier after
seeing the result. If a predeclared mechanical rule excludes a sample, retain
that sample and publish summaries both with and without the exclusion.

Compare variance only within one matching host class and workload. Use the
previous accepted p95 as the drift denominator. Drift at or below 10% is the
noise envelope and does not support an improvement or regression claim. Drift
above 10% requires investigation. Drift above 20%, or three consecutive
same-direction envelope breaches, blocks re-baselining and requires an issue
with the raw vectors and fingerprints.

`fszero-w2g.45` owns raw-trial and published-summary enforcement;
`fszero-tep8` owns CI ratchets. Those implementation vehicles do not weaken
this policy while their work remains open.

## Profilable release builds

Published latency/throughput claims and any CPU profile artifacts must be
produced under Cargo profile **`release-perf`** with symbols retained and
frame pointers available for stack unwinding:

| Knob | Contract |
| :-- | :-- |
| Cargo profile | `--profile release-perf` (never plain `--release` for published numbers) |
| Symbols / strip | `strip = false` (see `[profile.release-perf]` in root `Cargo.toml`) |
| Debug line tables | `debug = "line-tables-only"` on that profile |
| Frame pointers | Required for stack profiles; stable Cargo cannot set this on a profile field |

Plain `cargo build --release` / `target/release/*` is **not** an honest published
surface: release defaults may strip, multi-CGU, and omit line tables. Runners
must default to `target/release-perf` (see closed bead `fszero-lmkh`).

The `release-perf` profile keeps line tables and symbols, but Cargo profiles
cannot enable frame pointers on stable Rust. Any samply, perf, flamegraph, or
other CPU stack-profile claim must build through `scripts/profile_build.sh`.
The wrapper preserves existing `RUSTFLAGS` and appends
`-C force-frame-pointers=yes` last (closed bead `fszero-k0tg`). Do not use a
bare `cargo build --profile release-perf` for stack-profile claims.

Build the profiling harness through the required RCH path:

```bash
rch exec -- env CARGO_TARGET_DIR=/tmp/rch_target_fszero_profile \
  ./scripts/profile_build.sh -p fs-zero --bench perf_harness
```

Use `./scripts/profile_build.sh --print-command ...` to inspect the resolved
flags and Cargo command without compiling. Fingerprints for published runs
must record `cargo_profile: release-perf` (see Environment fingerprint and
`scripts/benchmark.py` / `scripts/env_fingerprint.py`).

Related beads: `fszero-k0tg` (force-frame-pointers wrapper), `fszero-lmkh`
(runners default to release-perf), `fszero-lghz` (samply/flamegraph runbook
in [`docs/profiling.md`](profiling.md)), `fszero-act0` (macOS sample/xctrace
fallback in [`docs/profiling-macos.md`](profiling-macos.md)), `fszero-tep8`
(CI surface ratchets).

## Closure checklist for benchmark beads

- [ ] Runner script committed; number reproduces from a clean checkout.
- [ ] Corpus / gold set committed or generated by a committed script.
- [ ] Baselines ran under identical conditions at best documented config.
- [ ] Losses and regressions filed as beads and included in the report.
- [ ] Published numbers carry claim annotations and cite the benchmark commit.
- [ ] Sample count is at least 20, or a conservative-tail exception is explicit.
- [ ] Latency claims include p50/p95/p99 plus the ordered raw trial vector.
- [ ] Warmup and outlier rules were declared before the run; excluded values remain published.
- [ ] Variance drift follows the 10% investigation and 20%/three-breach escalation rules.
- [ ] Scenario fingerprint is complete and cache state is one of the four named values.
- [ ] Absolute comparisons match host class and declare isolation; contaminated runs are rejected.
- [ ] Binary/bench built with `--profile release-perf` (symbols retained; fingerprint `cargo_profile=release-perf`); plain `--release` is not used for published claims.
- [ ] CPU stack-profile artifacts built via `scripts/profile_build.sh` (frame pointers on); bare release-perf without force-frame-pointers is not claimed as a stack profile.
- [ ] `uv run python scripts/claims_audit.py` exits 0.

## CPU profile promotion (clone-visible)

Local run dirs under `tests/artifacts/perf/` are gitignored. To retain a CPU
profile that survives `git clone`, promote the min set into
`docs/evidence/perf/<run-id>/` per [`docs/evidence/perf/README.md`](evidence/perf/README.md)
(fingerprint + one of `flame.svg` / `cpu.json` / `sample.txt` + hotspot_table).
Worked example: `docs/evidence/perf/20260704_001/PROMOTED.md`. Do not commit
multi-MB raw traces without size review. Force-add under the scratch tree is a
last resort for small allowlisted names only.
