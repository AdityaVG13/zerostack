# CDC chunk and dedup benchmark

Generated by:

```sh
rch exec -- cargo test --test cdc_properties -- --nocapture
```

Spark worker: `spark-1672`. RCH job: `job-47bc082e`. The deterministic
23,000-byte GTNH quest-line corpus contains 400 recipe/progression records,
truncated at exactly 23,000 bytes. The synthetic corpus is 100,000 seeded
pseudo-random bytes. Each workload applies 1,000 deterministic single-byte
edits across the complete input.

| Corpus | Bytes | CDC chunks | Median invalidated | Full-file baseline |
|---|---:|---:|---:|---:|
| GTNH quest lines | 23,000 | 12 | 1 | 12 chunks |
| Synthetic | 100,000 | 37 | 1 | 37 chunks |

The measured median is below the acceptance ceiling of three chunks. Every
reported invalidation is an exact old-manifest `[start,end)` chunk; the
1,000-case randomized insert/delete/replace property rejects partial ranges.

Two 100,000-byte files shared an identical 80,000-byte prefix. The second file
had 67 chunks, 64 durable-index hits, and a measured 95.5% hit rate. This
exceeds the 40% acceptance floor. After dropping and reopening the durable
store, indexing the first image again reused every chunk. Content refs expanded
byte-for-byte to each manifest range.

The no-CDC baseline invalidates the entire file and has no sub-file or
cross-session identity. FSZero uses deterministic 512-byte minimum, 2,048-byte
target, and 8,192-byte maximum FastCDC-style boundaries. Chunk bytes remain in
the existing content-addressed payload tier; `chunk_blobs` deduplicates them
by SHA-256, while `file_chunks` atomically publishes ordered render segments.
